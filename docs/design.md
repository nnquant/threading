# Threading 设计说明

## 要解决的问题

同时为多个组织做多个策略项目，每个项目里又有多条策略线并行推进。难点不在“记任务”，而在：

- 线太多，**不知道哪条线停了、哪条在等人、哪条缺了下一步**；
- 在组织和项目之间来回切换，**回到一条线时想不起它走到哪、为什么这么做**；
- 研究类工作的进度用百分比描述不准确，**“还没想清楚”和“只剩执行”是两种完全不同的状态**；
- 同时开的线越来越多，**没有人提醒“该收一收了”**。

## 调研：流行方案各自擅长什么

| 方案 | 核心做法 | Threading 借鉴了什么 |
| --- | --- | --- |
| [Linear](https://linear.app/docs/linear-method) | 层级为 Workspace → Team → Project → Issue；项目有健康度（On track / At risk / Off track）和带健康度的[进展更新](https://linear.app/docs/initiative-and-project-updates)；键盘优先、Ctrl+K 命令面板 | 项目健康度与“进展”记录；命令面板；键盘操作；克制的列表密度 |
| Basecamp《Shape Up》 | 用**山丘图**表示不确定性：上坡是“还在摸索”，下坡是“只剩执行” | 每条策略线一个山丘位置，项目页有可拖动的山丘图 |
| GTD（Getting Things Done） | 每个进行中的项目都必须有明确的**下一步**；单独的**等待清单**；**每周回顾** | 下一步待办、“缺少下一步”提醒、等待对象与等待天数、周回顾流程 |
| Kanban | 看板按阶段排列，**限制在制品（WIP）** | 按研发阶段的看板，拖动换阶段；进行中上限提醒 |
| QuantConnect 等量化平台 | 策略按证据逐级推进：研究 → 回测 → 模拟 → 实盘 | 六个固定阶段：构想、研究、回测、模拟、实盘、退役；策略线上记关键指标 |
| Notion / ClickUp / Plane | 高度可定制的数据库与多视图 | 只取“同一份数据多种视图”（列表 / 看板 / 山丘图 / 时间线），刻意不做自定义字段，避免变成维护负担 |

结论：通用工具要么偏团队协作（Linear、Asana、Plane），要么过于自由（Notion）。一个人横跨多组织管理研究线，更需要**跨组织的注意力视图**和**研究进度的正确表达**，所以做成本地优先的单人桌面工具。

## 模型

```text
组织 Organization ── 客户、基金或自营研究
└─ 策略项目 Project ── 健康度、状态、目标、目标日期、进展
   └─ 策略线 Thread ── 阶段、状态、优先级、山丘位置、等待对象、标签、指标、说明
      ├─ 子策略线 Thread ── 同一个项目里从这条线分出的线，可以继续往下分
      ├─ 下一步 Todo ── 第一条未完成的就是“下一步”，可设截止日期
      └─ 记录 Entry ── 笔记、决策、结果；阶段/状态/上级变更自动记录
```

策略线可以无限嵌套：一个因子拆成几个板块，一个板块再试几种换月规则。子策略线就是一条完整的策略线，有自己的阶段、状态、下一步和记录；层级只回答“它是从哪条线分出来的”。几条约定让层级不变成负担：

- 上级和子策略线总在同一个项目里，移到别的项目时整棵子树一起走，删除时一起删。
- 推进子策略线也算推进上级，所以上级不会因为工作都在子策略线里而显示“停滞”；上级自己没有待办、但有进行中的子策略线时，也不算“缺少下一步”。
- 阶段和状态不向下传递：搁置或结束上级，不会替你结束它的子策略线。

两个正交维度刻意分开：

- **阶段 stage**：这条线在研发流程的哪一步（构想 → 研究 → 回测 → 模拟 → 实盘 → 退役）。
- **状态 state**：我现在对它的投入（进行中 / 等待 / 搁置 / 已结束）。

## 视图

- **焦点**：跨所有组织，只列需要处理的事——七天内到期的下一步、等待中的线（按等待时长）、停滞的线（超过设定天数没有推进）、缺少下一步的线、有风险或偏离的项目，以及超过进行中上限的提醒。
- **全部策略线**：列表（按项目 / 阶段 / 状态 / 优先级分组）、按阶段的看板，或线程图。项目页的策略线标签里也有同样三种布局。列表和线程图里子策略线挂在上级下面，用细线连成树，可以折叠；上级不在同一组（比如按阶段分组、被筛选掉或已结束未显示）时，标题前用灰字写出上级。看板按阶段分列，卡片上方写上级、底部显示子策略线数量。
- **组织**：项目一览，每个项目的进行中策略线沿阶段线分布。
- **项目**：策略线、山丘图、动态（项目进展与所有策略线记录）。
- **周回顾**：逐条过一遍进行中和等待中的线，确认阶段、山丘位置和下一步，记一笔，标记已回顾。
- **策略线详情**：右侧面板，所有属性、下一步、指标、说明和时间线都在这里。顶部路径一直写到上级策略线，可以改上级；“子策略线”一节画出这条线下面的整棵树，并能直接分出新的子策略线。
- **标签页**：标题栏中间是标签页。第一个标签页承载焦点、全部策略线、周回顾和组织页，侧栏里点这些视图都在它里面切换；项目在各自的标签页里打开，同一个项目只开一个。每个标签页有自己的详情面板，隐藏的标签页保持挂载，切回来时滚动位置、筛选和打开的策略线都还在；标签列表存在本机，重启后恢复。搜索框移到右上角，窄窗口下收成图标。
- **记录编辑器**：写记录的框右上角的按钮把已写的内容带进一个单独的编辑器标签页。编辑器所见即所得（TipTap），存的仍是 Markdown，时间线照常渲染；Markdown 语法边输入边转换。图片可以粘贴、拖入或从本机选择，保存成数据目录 `images` 里的文件，正文只写 `attachment:<id>` 引用，显示时经后端读出再转成 blob URL。公式存成 `$…$` 和 `$$…$$`，编辑器和时间线都用 KaTeX 排版；ChatGPT 风格的 `\(…\)`、`\[…\]`（包括 0.1.0 编辑器转义后存下的写法）在显示和打开编辑器前统一改写成美元符号，单独的 `$` 按 Pandoc 的规则判断，价格不会被当成公式。草稿随输入保存在本机，关掉标签页前有文字会先确认；原来的写记录框里会出现“继续编辑草稿”按钮。发布后回到来时的标签页。

## 线程图，以及为什么不用甘特图

甘特图画的是计划：预估的起止日期和任务依赖。研究线的工期估不准，线与线之间也很少有依赖，甘特条只能反复重画，而且看不出哪条线停了、在等谁。

线程图只画**已经发生的事**和**已经承诺的日期**：

- 每条策略线是一根从创建延伸到今天的线。线越粗，阶段越靠后；实线是进行中，虚线是等待，点线是搁置。一条进行中的线从最近一次推进开始逐渐变淡，到停滞天数时最淡。已结束的线在结束处画一道短竖线。
- 线上的结：竖线表示换阶段，空心圆是笔记，菱形是决策，实心圆是结果，线下的小刻度是完成的待办。
- 今天右侧只画待办的截止日（空心圆，逾期的标红）和项目目标日期（虚竖线），并写出这条线现在最需要知道的一件事：等了多久、在等谁，停了多少天，缺少下一步，或者下一步是什么。
- 子策略线排在上级下面，从它被创建的那天起，用一段圆角细线从上级的线上弯下来接到自己的起点，像一根分出去的线。创建早于所看时间范围的子策略线只靠名字列的缩进表示层级。
- 历史由自动记录的阶段和状态变更倒推出来（`threadSpans`）：从当前值出发，按时间倒序用每条变更的 `from` 还原，删掉一条变更记录只会让一个分界点变模糊。

山丘图回答“现在每条线卡在哪种不确定性里”，线程图回答“过去几周每条线的节奏”。

## 视觉

沿用 Dropping 的语言：白底墨色、Noto Sans、13px、细线分隔、4px 圆角、自绘标题栏和状态栏。语义色只用于健康度、逾期和停滞，组织用小色块区分。

糖果色是一套红橙黄绿青蓝紫的浅色，用法沿用 Dropping 的文件图标：浅色底上总是压深色墨迹。每种颜色另有一档同色系的深色，用于描边和小图形，浅色在白底上也不需要黑描边。糖果色只用在两处关键元素上：

- **阶段**：沿彩虹顺序排列，构想红、研究橙、回测黄、模拟绿、实盘蓝、退役紫（青留给焦点视图）。糖果浅色用于填充（阶段图标底色、看板列头色条、线程图底色），深色用于扇形和描边。
- **阶段图标**：列表、看板、命令面板和图例里，阶段用一个小饼图表示：比糖果色更浅的圆底上用深色填一块扇形，每进一个阶段多填六分之一，退役是满圆。一个图标同时说明“是哪个阶段”和“走到第几步”，后面的阶段名用同一阶段的深色文字，不用色块标签。详情面板里可点击的阶段选择器保留“线 + 结点”的形式：轴线加粗，走过的阶段是实心大圆点，当前结点换成放大的阶段图标；当前阶段的名字用阶段色，走过的是黑色，没走到的保持灰色。
- **焦点的分区**：下一步日程（青）、等待中（黄）、停滞（橙）、缺少下一步（紫）、需要关注的项目（红）各有一个糖果色图标块。

小结点的描边和底色取自所在行的背景（`--surface`），悬停或选中的行上不会出现白色光圈。唯一的“记忆点”是**线**：阶段用一根带结点的细线表示，时间线上的每条记录也是线上的一个结。

## 前后端分工

- 前端（`src/`）：React 19 + TypeScript，只通过 [`src/bridge.ts`](../src/bridge.ts) 调用后端命令，用后端返回的 `Change` 合并状态。浏览器预览使用 [`src/preview.ts`](../src/preview.ts) 中遵循同一契约的内存实现，示例数据来自 [`src/demo.ts`](../src/demo.ts)。桌面版不提供示例数据的界面入口，只能在搜索框输入 `ENABLE_SAMPLE_DATA` / `DISABLE_SAMPLE_DATA` 添加或清理。
- 后端（`src-tauri/`）：Rust + Tauri 2 + SQLite，规则见 [backend-contract.md](backend-contract.md)，实现说明见 [backend-notes.md](backend-notes.md)。
